# F073 RFC：统一 .is 编辑器 JSSDK 与语义化场景操作接口

## 1. 摘要

IdeaSketch（`.is`）目前没有一个稳定、类型化的 JSSDK。画布命令、Excalidraw 原始 API、页面和 Camera 闭包、Agent Tools 以及编辑器绑定分散在不同层级；新增能力通常只能在某一个入口上打补丁。本文提出一个由 IdeaSketch 自有的 `IdeaSketchSdk` facade 统一承载的接口边界，并把文本作为完整场景模型的一部分，而不是独立的临时接口。

所有场景写操作都通过一个语义化 `applyPlan()` 事务入口完成。独立文本、形状内文本、文本内容和字号/样式调整，与形状、箭头、绑定、移动、缩放和删除使用同一套 ChangeSet、稳定引用、读取前置条件、版本校验和原生 Excalidraw Undo 路径。现有 Agent Tools 和 UI 命令保留兼容层，但不再继续扩大原始 `any` API 的公共契约。

## 2. 背景与问题

当前实现已经具备可复用的安全边界：编辑器绑定了文档身份、revision、source fingerprint、只读状态、取消状态和挂载状态；Agent 的 `apply_drawing_plan`、`apply_layout_plan` 会通过活动 Page 的原生编辑器事务写入，并参与正常的 dirty、auto-save、recovery 和 Undo 流程。F070/F071 证明了语义化形状、箭头、绑定、移动和缩放可以共用这条路径。

但接口仍然是分散的：

| 当前表面 | 已有方法或能力 | 当前问题 | RFC 归类 |
| --- | --- | --- | --- |
| `SlideCanvasCommandApi` | `exportDrawio`、`openImageExport`、`changeCanvasBackground`、`clearCanvas` | 仅是组件级命令，不能被其他调用方复用 | facade 的 `io`、`view`、`scene` 命令 |
| 原始 Excalidraw API | 读取 `getSceneElements()`、`getSceneElementsIncludingDeleted()`、`getAppState()`、`getFiles()`；写入 `updateScene()`、`addFiles()`；视图/事件 `setActiveTool()`、`scrollToContent()`、`refresh()`、`setToast()`、`onChange()`、`onScrollChange()`、`onPointerDown()`、`onPointerUp()` | 通过 `any` 传递，暴露底层数据结构，容易绕过文档安全和持久化边界 | 仅保留为内部 adapter；对外提供类型化、受限语义接口 |
| `IdeaSketchEditor` 页面闭包 | `selectPage`、`addPage`、`duplicatePage`、`importPage`、`renamePage`、`reorderPage`、`deletePage` | 页面能力与场景能力没有统一的目标、结果和错误模型 | facade 的 `pages` |
| `IdeaSketchEditor` Camera/导入导出闭包 | `selectCamera`、`deleteCamera`、`reorderCameraList`、`handleAddCamera`、`startPresentation`、`exportActivePageAsExcalidraw`、`exportActivePageAsIdeaSketch`、`handleConvertSelection`、`changeCanvasBackground`、`clearCanvas`、`exportDrawio`、`openImageExport` | 只能通过 React 闭包调用，无法形成可测试的 SDK 契约 | facade 的 `cameras`、`io`、`scene`、`view` |
| IdeaSketch Agent Tools | `read_document_outline`、`read_active_page`、`add_page`、`delete_page`、`reorder_page`、`replace_page_elements`、`apply_drawing_plan`、`apply_layout_plan` | Tool schema 是唯一较完整的语义入口，但只覆盖形状/箭头/布局，缺少文本和统一操作模型 | 兼容适配到 `IdeaSketchSdk` |
| Agent Editor Binding | `buildContext()`、`createToolExecutor()`、`describeChangeSet()`、`applyChangeSet()` | 绑定接口是编辑器内部协议，不是可复用的 JSSDK facade | facade 的 host adapter |
| Camera 私有 API | `getSceneElements()`、`setActiveTool()`、`updateScene()` | 为 Camera 绘制测试和宿主控制服务，不能作为公共 JSSDK | 保持私有，仅由 adapter 使用 |

缺少统一边界会造成四类实际风险：

1. 文本无法和形状、箭头共享同一套引用、绑定和 Undo 语义。
2. 新入口容易复制 revision、只读、取消和外部变更检查，最终出现行为分叉。
3. `any` 原始 API 让调用方可以构造任意 Excalidraw JSON，公共契约会被上游版本牵着走。
4. 页面、Camera、视图、导出和场景修改的能力无法通过 capability 发现、版本化和渐进迁移。

## 3. 目标

1. 提供唯一的、类型化的 `IdeaSketchSdk` facade，覆盖当前 `.is` 编辑器的可复用读取、页面、场景、文本、Camera、视图和导入导出能力。
2. 让独立文本、形状内文本、文本替换、字号和文本样式调整成为一等场景操作。
3. 让 UI、Agent 和未来外部 JSSDK 调用方共用同一个 ChangeSet 校验和编辑器事务边界。
4. 保留 `page:<id>`、`element:<id>` 等稳定引用，并以 captured revision 与 source fingerprint 防止过期写入。
5. 保证一次成功的场景计划对应一次原生 Excalidraw history capture；失败、取消、只读、未读取、跨 Page 或不支持目标时不产生场景变化。
6. 保留现有 Agent Tool 的输入和行为兼容性，把旧入口适配到新的统一操作模型。
7. 通过 capability/version 协商逐步扩大能力，不把任意 Excalidraw JSON 或文件写入暴露给调用方。

## 4. 非目标

- 本 RFC 不实现代码，也不批准任何具体实现计划。
- 不重做 `.is` 文件格式，不要求已有文件迁移；文本仍以可编辑的原生 Excalidraw 元素保存。
- 不支持富文本 span、Markdown 渲染、图片文字、任意自定义容器或跨 Page 的单事务修改。
- 不向公共 JSSDK 暴露任意 Excalidraw JSON、原始 `AppState`、底层 event emitter 或直接文件写入。
- 不新增独立的文本编辑器 UI；画布内编辑仍由 Excalidraw 负责。
- 不改变通用 Agent runtime、模型 provider、Thread 或 Tool approval 的职责。
- 不在本阶段承诺把 SDK 发布为独立 npm 包；先在应用内形成稳定边界，待第二个编辑器复用后再评估拆包。

## 5. 决策

### 5.1 统一 facade 与分层

新增一个由 IdeaSketch 拥有的类型化 facade。下面是公共能力分层；具体命名可在开发计划中做不改变语义的调整：

```text
IdeaSketchSdk
├── context       # 文档、Page、revision、capability、只读状态
├── pages         # Page 列表、选择、添加、复制、导入、重命名、排序、删除
├── scene         # 读取、清空、统一 applyPlan、受控的 legacy replace
├── shapes        # 形状创建与语义属性
├── connectors    # 箭头创建与端点绑定
├── text          # 独立文本、形状内文本、内容与样式
├── cameras       # Camera 列表、添加、选择、删除、排序、Present
├── view          # 背景、工具、滚动、刷新和受控提示
└── io            # Excalidraw、`.is`、draw.io 和图片导出
```

`IdeaSketchSdk` 是调用方契约；原始 Excalidraw 实例只存在于 `ExcalidrawAdapter` 和挂载的编辑器 host 内。UI 闭包、Agent Editor Binding、Camera 私有 API 均改为调用 facade 或其 adapter，不再各自实现写入规则。

### 5.2 读取、引用与 capability

- 所有需要目标元素的写操作都要求先成功读取当前活动 Page。
- 读取结果只返回有界的语义摘要：`element:<id>`、类型、bounds、文本、绑定关系、z-order 和必要的 group 标记；截断必须显式标记，截断结果不能满足需要完整目标集合的写操作。
- Page、元素和文档均使用稳定引用；计划内新建元素可使用只在该计划内有效的临时 `ref`。
- 每个写计划携带文档 id、Page id、captured revision 和 source fingerprint。编辑器在应用前重新校验这些字段以及当前挂载、只读、取消和外部变更状态。
- `context.getCapabilities()` 返回操作、样式、支持容器、限制和协议版本。未知操作、未知样式或超出限制的请求必须 fail closed。

### 5.3 统一场景事务

场景内容修改统一进入以下语义入口（示意契约，不是实现代码）：

```text
applyPlan({
  target: { documentId, pageId, baseRevision, sourceFingerprint },
  operations: [...],
  requestId?
}) -> { changeSetId, status, createdRefs, summary }
```

执行顺序固定为：读取前置条件 → 解析和规范化 → 校验全部操作及关系 → 在内存中构建完整新场景 → 一次 `updateScene` 原生 capture → 交回现有文档 session 的 dirty、auto-save、recovery 和外部变更流程。任一步失败都不得调用写入 API。`requestId` 用于防止同一调用重放造成重复修改；取消在提交前生效，提交后由原生 Undo 负责回退。

Page 结构和 Camera 命令也使用相同的文档身份、只读、取消和持久化守卫，但不伪装成 Excalidraw canvas history。导出、视图和事件订阅属于 facade 的非场景命令，不改变 ChangeSet 语义。

### 5.4 统一操作集合

第一版 canonical operation 集合如下：

| 操作 | 目标 | 语义 |
| --- | --- | --- |
| `create-shape` | 计划内 ref | 创建受支持的矩形、椭圆或菱形，并允许携带初始文本声明 |
| `create-arrow` | 计划内 ref | 创建箭头几何和受支持的样式 |
| `bind-arrow` | 箭头 ref + 元素 ref | 维护箭头端点与形状的双向绑定 |
| `create-text` | 计划内 ref | 创建独立文本元素，使用受限位置、文本长度和样式 |
| `bind-text` | 文本 ref + 矩形/椭圆/菱形 ref | 把文本放入形状容器并维护 `text.containerId` 与容器 `boundElements` |
| `set-text` | `element:<id>` 或形状 ref | 替换文本内容；形状目标解析为其唯一绑定文本 |
| `set-text-style` | 文本或形状 ref | 修改字号、字体、颜色、对齐、透明度、行高等允许字段 |
| `move-element` | `element:<id>` | 按有界 delta 移动元素；绑定文本随容器同步 |
| `resize-element` | `element:<id>` | 按有界尺寸调整元素，并刷新绑定文本尺寸 |
| `delete-element` | `element:<id>` | 受控删除元素，同时清理箭头和文本关系 |
| `set-background` / `clear-scene` | 当前 Page | 统一当前画布命令的语义入口 |

具体限制由协议常量和 capability 返回；初始文本限制建议为单次计划最多 40 个操作、单个文本最多 4,000 个字符、字号 6–200，并对坐标、尺寸、透明度和枚举样式使用现有 Agent 的有界校验方式。实现计划不得通过放宽限制来绕过安全边界。

### 5.5 文本模型与关系不变量

文本能力必须同时覆盖以下场景：

1. **独立文本**：在 Page 上创建可编辑的原生 text 元素，支持内容、位置和受限字体样式；尺寸由 Excalidraw 文本测量和 `restoreElements` 修复。
2. **新形状内文本**：`create-shape` 可以在同一计划声明初始文本，或随后使用 `bind-text`；整个计划仍只有一次 native capture。
3. **已有形状内文本**：只允许绑定到读取结果中可见且受支持的矩形、椭圆或菱形；不存在可用容器、容器已有冲突文本或目标来自其他 Page 时拒绝。
4. **内容与字号调整**：`set-text` 和 `set-text-style` 可以直接定位已有 text，也可以语义定位形状容器；修改不应重写无关元素。

应用后必须满足：文本的 `containerId` 与形状的 `boundElements` 互相一致；形状移动或缩放时绑定文本位置和尺寸保持一致；箭头绑定、group、files 以及未涉及元素保持不变；恢复后的 native scene 仍可由 Excalidraw 继续编辑。

### 5.6 兼容层与迁移

保留旧入口，但把它们降级为 facade 的适配器：

```text
apply_drawing_plan ─┐
apply_layout_plan  ─┼─> IdeaSketchSdk.applyPlan()
旧 UI/页面命令     ─┤
旧 Camera/导出命令 ─┘
```

- `apply_drawing_plan` 继续接受现有形状、箭头和绑定输入，并增加文本操作的兼容映射。
- `apply_layout_plan` 映射到同名 canonical 操作，保持稳定元素引用和已有边界。
- `replace_page_elements` 暂时保留为遗留 Agent 能力，仅在受信任的兼容 adapter 中执行；新 JSSDK 不暴露任意场景 JSON，并将该入口标记为 deprecated，未来以语义 `scene.replace` 或明确的批量操作替代。
- `SlideCanvasCommandApi`、页面闭包和 Camera 私有 API 只保留薄适配，不再拥有独立的 revision、绑定或持久化逻辑。
- 第一个版本只提供应用内 TypeScript SDK。待另一个编辑器复用同一 host/ChangeSet 契约后，再决定是否发布独立包。

迁移不改变已保存 `.is` 数据结构，因此可通过 feature flag 或按调用方逐步切换；若新 adapter 出现回归，可回退到兼容入口而不需要文件回滚。只有在所有调用方完成迁移且至少经过一个稳定版本后，才考虑移除原始 `any` 暴露和旧别名。

## 6. 已考虑的重要替代方案

### 方案 A：只在 `apply_drawing_plan` 上增加文本字段

拒绝。它能最快覆盖独立文本和形状文本，但会继续把 JSSDK、Agent、页面命令和原始 Excalidraw API 分割开，无法解决统一版本、能力发现、事务和迁移问题。

### 方案 B：新增一个独立 `TextSdk` 或 `apply_text_plan`

拒绝作为架构主线。可以保留 `apply_text_plan` 作为便利别名或兼容 Tool，但文本与形状容器、箭头、布局和 Undo 有共同的场景关系，独立事务会产生重复校验和绑定不一致。

### 方案 C：直接把 Excalidraw API 作为公共 JSSDK

拒绝。调用方将依赖上游版本和任意 JSON，能够绕过 revision、外部变更、只读和持久化守卫，也无法对文本容器关系提供稳定语义保证。

### 方案 D：所有修改都使用整页 JSON replace

拒绝作为默认方式。整页替换无法表达最小意图，容易覆盖并发或无关元素，且不利于稳定引用、单步 Undo 和可观察的变更摘要。遗留 replace 仅作为受限兼容能力保留。

### 方案 E：立即发布独立 npm SDK 并一次性移除旧接口

暂缓。当前只有一个编辑器真正消费该边界，立即拆包会固化尚未经过第二编辑器验证的契约并增加迁移风险。先形成应用内 facade，再以 capability 和版本作为外部化前提。

## 7. 风险与缓解措施

| 风险 | 缓解措施 |
| --- | --- |
| facade 范围过大，公共 API 难以演进 | 分层命名空间、显式 capability、协议版本和 deprecated 别名；只公开语义字段 |
| text/container 关系损坏 | 统一 `bind-text`/`set-text` 解析，应用前全量关系校验，应用后调用 `restoreElements`，并覆盖保存、重开、Undo 测试 |
| Agent 或 UI 重复应用同一计划 | `requestId`、ChangeSet ledger 和一次性 native capture；重复请求返回已有结果或 fail closed |
| 过期读取覆盖外部修改 | 强制 document/Page/revision/source fingerprint 校验，外部变更或 source marker 不匹配时拒绝 |
| 大场景读取和文本测量造成卡顿 | 有界语义读取、单计划操作上限、文本长度/坐标/尺寸限制，禁止公共接口返回完整原始 scene |
| 兼容 adapter 与新 facade 行为分叉 | adapter 只负责 schema 转换，实际校验、构建和应用全部进入同一 canonical pipeline |
| 原始 Excalidraw 上游升级破坏字段 | 将上游类型和 `updateScene` 细节隔离在 adapter；对外只承诺 IdeaSketch 自有协议 |
| 新能力被误用于直接写文件 | SDK 不提供文件路径或写盘方法，所有写入回到挂载编辑器和既有保存/recovery 流程 |

## 8. 发布、回滚与验证边界

### 发布顺序

1. 先建立类型、capability 和 adapter，不改变旧入口的可观察行为。
2. 将 Agent、UI 页面/Camera 命令和画布命令切换到 facade，并保留兼容别名。
3. 加入文本 canonical operations，验证独立文本、已有/新建形状内文本、内容替换、字号和样式调整。
4. 在至少一个完整 `.is` 保存、重开、Undo、auto-save 和外部变更流程中验证后，再宣布 JSSDK v1 稳定。
5. 稳定版本后再评估移除原始 `any` 暴露、遗留 replace 和应用内 facade 的外部拆包。

### 回滚边界

回滚只切换调用方到旧兼容 adapter；不需要迁移或回滚 `.is` 文件，因为文本仍是原生可编辑元素。若某个新操作已经成功提交，使用 Excalidraw 原生 Undo 或现有 recovery 机制恢复，不通过直接文件覆盖回滚。

### 必须保留的验证证据

- 每个当前方法在 facade 中有明确归属、可见性和兼容策略。
- canonical `applyPlan()` 对形状、箭头、绑定、布局和文本使用同一套 target/revision/fingerprint/取消/只读校验。
- 文本绑定不变量、无关元素保留、箭头关系保留和一次 native capture 有自动化测试。
- malformed、未读取、过期、跨 Page、只读、取消、切换文档、超限和不支持容器请求均无场景变化。
- TypeScript build、相关 Agent/editor contract tests、保存重开和 `git diff --check` 通过。

## 9. 可观察的批准条件

RFC 进入 `approved` 前，需要确认以下决策已经被接受：

- 接受 `IdeaSketchSdk` facade 作为 `.is` 编辑器唯一的 JSSDK 方向，原始 Excalidraw API 仅限内部 adapter。
- 接受 `applyPlan()` 作为所有场景内容写入的 canonical 事务入口，以及页面/Camera/IO 命令与场景事务的边界。
- 接受 `create-text`、`bind-text`、`set-text`、`set-text-style` 与现有形状/箭头/布局操作共用 ChangeSet、稳定引用和一次 native Undo capture。
- 接受第一版形状文本只支持矩形、椭圆和菱形，文本限制、样式枚举和单计划上限由 capability/协议约束。
- 接受 `apply_drawing_plan`、`apply_layout_plan` 和现有 UI/Agent 入口保留兼容适配；`replace_page_elements` 只作为 deprecated 的受信任遗留能力。
- 接受 RFC 批准后仍需另行创建并审批新的实现计划；RFC 本身不授权编码或发布。
