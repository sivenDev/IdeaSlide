## 1. 产品摘要

Enacta V2 是一个本地优先、持续存在、可被信任的个人 AI 同事。

用户打开产品后，首先面对的不是 Workspace、文件树或编辑器，而是 Enacta Agent。用户通过文字或声音表达目标、问题、想法和决定；Enacta 结合经过授权的数据、历史、记忆和当前任务，理解意图、澄清不足、调用能力、推进工作，并把过程转化为可审查、可编辑、可执行和可持续维护的成果。

Markdown、IdeaSketch、Workspace、未来领域编辑器以及临时 Web 视图不再是产品主体。它们是 Enacta 在人需要查看数据、共同思考、修改结构、审核变化或交付成果时按需打开的视图和工具。

V2 的核心关系是：

```text
用户表达意图、提供判断并承担关键决定
                  ↕
        Enacta 持续理解、记忆和推进
                  ↕
数据 / 记忆 / 权限 / 任务 / 活动 / 成果
                  ↕
对话卡片 / Markdown / IdeaSketch / 领域编辑器 / Web 视图
```

一句话定位：

> **Enacta 是一个持续理解用户、调用合适能力，并把模糊意图推进为真实成果的个人 AI 同事。**

面向用户的简洁表达：

> **告诉 Enacta 你想完成什么，它和你一起把事情做完。**

### 1.1 V2 首版唯一承诺

长期愿景可以很大，但首版产品只能有一个清晰承诺：

> **把一个用户暂时说不清楚的真实任务，在有限且可见的权限范围内，推进成一份可审核、可修改并保存为真实文件的成果。**

首版不是先证明 Enacta 拥有多少能力，而是先证明以下完整体验成立：

```text
用户表达一个模糊目标
→ Enacta 只澄清会改变结果的关键问题
→ 必要时打开 IdeaSketch 共同形成结构
→ 在明确授权内生成可审查成果
→ 用户修改、接受并保存为真实 Artifact
→ Enacta 留下行动回执和可选择的记忆候选
```

“个人 AI 同事”是 Enacta 通过一次次可靠完成工作逐渐获得的用户认知，不是安装完成后就自动成立的身份。多分身、成熟记忆、主动协作、插件生态和环境式存在都必须建立在这个首版承诺已经被真实用户验证之后。

## 2. 从 V1 到 V2

### 2.1 V1 解决的问题

V1 建立了 Enacta 的可信工作基础：

- 真实文件 Workspace；
- Workspace Mode 与 Single File Mode 共用内核；
- Markdown 和 IdeaSketch 编辑器；
- 注册表驱动的编辑器扩展；
- 应用级通用 Agent；
- 文件安全、外部变更保护和原生 Undo/Redo；
- 持久化 Thread、流式活动、审批与受限 Tools；
- 本地优先、可见、可逆和可审计的产品原则。

这些能力是 V2 的资产，不是需要丢弃的旧产品。

### 2.2 V1 的产品中心仍然是工具

V1 虽然由 Agent 驱动，但用户看到的主体仍是 Workspace 和编辑器：

```text
Workspace → 选择文件 → 打开编辑器 → 在侧边栏调用 Agent
```

这仍然要求用户先理解产品结构，再决定使用哪个工具。Agent 是强大的助手，却不是用户与产品建立关系的中心。

### 2.3 V2 的核心反转

V2 将流程反转：

```text
与 Enacta 沟通
  → Enacta 理解目标和上下文
  → 选择合适的数据、能力与呈现方式
  → 必要时打开 Workspace 或编辑器
  → 用户参与判断和修正
  → Enacta 推进并交付成果
  → 经验沉淀为可治理记忆
```

产品主体从“可操作的工作空间”升级为“可长期协作的个人 AI 同事”。

## 3. 产品愿景

### 3.1 愿景

让每个人拥有一位真正了解自己、尊重边界、能够持续协作，并能把模糊想法推进为有效成果的 AI 同事。

### 3.2 使命

建立一个以人类意图和判断为起点，以可信 Agent 为执行伙伴，以数据和记忆为长期资产，以按需视图为协作媒介的个人工作系统。

### 3.3 长期承诺

Enacta 不只追求一次回答正确，而是追求长期合作越来越有效：

- 用户不需要重复解释稳定背景；
- Enacta 知道哪些信息重要，哪些可以淡忘；
- 不同角色使用同一个记忆基础，但不会越过隐私和权限边界；
- 模糊想法可以通过对话、绘图或其他媒介逐步澄清；
- 工作不会停留在建议中，而会进入可追踪的成果生命周期；
- 用户始终能看到、纠正、撤销、暂停或接管关键行为。

## 4. 核心产品定义

### 4.1 Enacta 是同事，不是聊天机器人

聊天机器人通常以一次回答为终点。Enacta 以任务结果为终点，并能够跨时间继续工作。

同事关系意味着 Enacta 应该：

- 理解当前目标而不只是回复最后一句话；
- 知道正在推进的事情和等待的决定；
- 主动发现表达不足，但不擅自替用户作重大决定；
- 选择适合共同思考和交付的工具；
- 对自己的数据来源、权限、动作和失败负责；
- 在重启、暂停或模型切换后继续已确认的工作；
- 从用户纠正中学习，而不是重复犯同样的错误。

### 4.2 Enacta 是一个身份，多种角色分身

用户面对的是同一个 Enacta。工作、生活和自定义分身是同一位同事在不同场景下的角色投影，而不是多个互不相关的机器人。

分身可以改变：

- 表达语气；
- 关注目标；
- 默认工具；
- 可使用的能力；
- 数据与记忆范围；
- 主动提醒策略；
- 输出格式偏好。

分身不能改变：

- 用户身份；
- 底层事实的一致性；
- Kernel 的安全边界；
- 已授予权限的真实范围；
- 用户对记忆和数据的控制权；
- 重要行为的审计与恢复规则。

### 4.3 数据和记忆是核心，UI 是投影

Enacta 的长期价值来自持续积累并正确使用的数据、记忆、任务、权限和成果。UI 只在需要时把这些内容转换为人可以理解和操作的形式。

这不意味着“所有内容都放进一个数据库”。V2 明确区分不同权威来源：

| 信息类型 | 权威来源 |
| --- | --- |
| 用户文档、画布、代码、HTML 与业务文件正文 | 用户真实文件 |
| Thread、Turn、Job、活动、审批、权限和恢复状态 | Enacta 应用自有存储 |
| 用户偏好、已确认事实和受治理长期记忆 | Enacta 记忆存储 |
| 邮件、日历、数据库等外部业务记录 | 对应外部系统 |
| 编辑器和 Web View 的当前界面状态 | 临时投影，不是事实来源 |

产品坚持：

> **Data-first 不等于 database-first；UI 不是事实来源，用户文件也不会被复制成另一份隐藏正文。**

### 4.4 成果比回答重要

Enacta 的成功不以生成多少文字衡量，而以是否形成用户认可的实际结果衡量：

- 一份可提交的汇报；
- 一个经过确认的计划；
- 一组真正完成的任务；
- 一次安全执行的自动化；
- 一个可维护的应用；
- 一个用户可以继续编辑、分享或运行的文件；
- 一个减少未来重复沟通的可靠记忆。

## 5. 目标用户与初期切入点

### 5.1 核心用户

**个人创造者、独立开发者和创业者**

经常从模糊想法开始，需要完成研究、规划、表达、设计、实现和交付，但不希望在大量工具之间切换。

**知识工作者和管理者**

工作价值主要来自提出问题、判断方向、协调信息和审核成果，希望 AI 承担资料整理、任务推进和重复执行。

**本地文件与隐私敏感用户**

愿意使用 AI，但要求数据可见、文件可迁移、权限可控、行为可恢复，不愿把长期工作完全锁在封闭 SaaS 中。

**需要跨工作与生活管理的人**

希望同一个 Agent 理解整体背景，但要求不同角色、信息和敏感内容保持清晰边界。

### 5.2 初期产品切入点

V2 第一阶段不以“万能 AI 同事”为目标，而以一个可验证承诺为中心：

> **用户可以把一个不清晰的真实任务交给 Enacta；Enacta 通过沟通、记忆、工具和必要的可视化协作，把它推进为用户认可的成果。**

三个闭环承担不同的产品职责，不以同等优先级同时建设：

| 职责 | 闭环 | 产品作用 | 初始阶段 |
| --- | --- | --- | --- |
| 首发获客与价值证明 | 模糊想法 → IdeaSketch 辅助表达 → HTML 或文档成果 | 让用户第一次体验“想法真的被做成成果” | Phase 1 |
| 留存与重复使用 | Workspace 文件和项目变化 → 周报、汇报和下一步行动 | 让 Enacta 进入用户已有工作并持续产生价值 | Phase 2 |
| 高频低摩擦入口 | 语音输入 → 决定、任务和资料 → 持续跟进 | 降低表达成本，提高日常使用频率 | Phase 2 |

Phase 1 只要求把首发闭环做到完整、可信、可重复理解；Phase 2 再验证同一闭环的重复质量，并扩展留存和高频入口。IdeaSketch 是首发场景的重要共同思考工具，但不是所有任务的强制步骤。

## 6. 产品本体模型

V2 使用以下产品对象统一交互、数据和执行语义。

### 6.1 User

拥有数据、记忆、权限和最终决定权的人。Enacta 的价值判断最终服务于 User，而不是模型、插件或自动化系统。

### 6.2 Enacta Identity

用户长期合作的同一个 Enacta 身份，承载关系连续性、共同历史和一致的安全边界。

### 6.3 Persona

Enacta 在特定场景下的角色投影。Persona 包含角色目标、语气、默认能力、记忆视角、数据范围和主动行为规则。

### 6.4 Context

当前任务可使用的数据、记忆、能力和默认权限申请范围。Work 与 Private 首先是受治理 Context；Persona 可以建立在 Context 之上，但不能借角色切换扩大 Context 或既有授权。

### 6.5 Intent

用户希望发生的变化。Intent 可以来自文字、声音、文件、画布、事件或外部数据，并可能在沟通中逐步明确。

### 6.6 Memory

能够提高未来协作效率、并具有来源、范围、可信度和生命周期的受治理信息。普通聊天记录不自动等于长期记忆。

### 6.7 Data Object

任务、决定、联系人、项目、日程、事实、偏好、指标或其他可结构化业务对象。Data Object 可以引用真实文件或外部系统，但不替代其权威正文。

### 6.8 Artifact

用户可继续使用的真实产物，例如 Markdown、IdeaSketch、HTML、代码、报告、图片、演示或导出包。

### 6.9 Outcome

一个被用户接受或通过明确规则完成的目标结果。Outcome 关联 Intent、计划、活动、权限、证据和 Artifacts。

### 6.10 Activity

Enacta 已执行、正在执行或等待执行的可见动作，包括 Tool call、审批、后台 Job、失败和恢复。

### 6.11 Permission

用户授予 Enacta 在特定目的、范围、时间和风险等级内执行能力的许可。

### 6.12 Capability

由 Kernel、Tool、Skill、Plugin、Connector、Workflow、编辑器或专业 Agent 提供的受限能力。

### 6.13 Workspace

真实文件和项目资料的工作区域，是数据与成果入口之一，但不再是产品启动中心。

### 6.14 Editor

对一种稳定业务数据提供语义化查看、编辑、验证和事务能力的注册组件。

### 6.15 View

根据数据生成的人类可读投影，包括对话卡片、表格、图表、编辑器界面和临时 Web 页面。View 可以消失或重新生成，不能成为隐藏事实来源。

## 7. Agent Home：产品的第一界面

### 7.1 启动体验

打开 Enacta 后，用户进入 Agent Home，而不是空白聊天框或默认 Workspace。

Agent Home 必须保持四个稳定区域，建立可预测的用户心智：

1. **今天**：建议优先处理、即将到期或适合继续的事项。
2. **等待我**：等待用户决定、授权、补充或审核的事项。
3. **正在推进**：Enacta 正在执行、等待外部条件或可以恢复的 Outcomes。
4. **最近成果**：最近完成、部分完成或需要继续维护的 Artifacts 与 Outcomes。

当前 Context 或 Persona、数据范围、文字与语音入口、Workspace、记忆和历史成果作为稳定导航与状态信息存在。对话、编辑器和生成 View 可以按任务变化，但不能替换这四个区域形成的整体框架。

示例：

```text
早上好。当前是 Work Context。

今天有三件事：
1. 产品汇报缺少最终数据，等待你授权读取销售表。
2. 昨天的讨论已经整理成 V2 产品草案。
3. 周报将在下午 4 点生成，发送前会让你确认。

你想先处理哪一件？
```

### 7.2 首次十分钟体验

首次使用应尽快产生一个真实成果，而不是先要求用户理解全部产品概念：

```text
0–1 分钟：选择一个 Workspace、单个文件或只使用本次提供的内容
1–2 分钟：说出一个当前真实但尚不清晰的目标
2–4 分钟：Enacta 询问一到三个会改变结果的关键问题
4–6 分钟：必要时打开 IdeaSketch，共同画出结构并复述理解
6–9 分钟：生成可审核的 HTML 或文档预览，标明来源和推断
9–10 分钟：用户修改或接受，保存为真实文件并查看行动回执
```

首次体验默认不要求用户：

- 创建多个 Persona；
- 设置自动衰减或压缩策略；
- 开启后台 Job；
- 安装 Plugins；
- 授权整个磁盘、全部历史或长期外部写入。

十分钟是产品目标而不是虚假时限。复杂任务可以更久，但用户应在十分钟内看到可判断的中间成果、明确下一步或真实阻塞原因。

### 7.3 对话不是唯一界面

Agent Home 以沟通为中心，但不把所有信息压缩成聊天气泡。任务状态、权限、成果、记忆和运行活动应使用稳定、可检查的结构化组件呈现。

### 7.4 当前状态必须真实

Enacta 应明确区分：

```text
理解中
→ 需要澄清
→ 计划待确认
→ 等待权限
→ 执行中
→ 等待外部条件
→ 等待用户审核
→ 已完成 / 部分完成 / 失败 / 已取消
```

不能用动画、虚假进度或拟人化文案掩盖真实状态。

### 7.5 主动但不打扰

Enacta 只有在以下情况主动出现：

- 用户承诺或任务即将逾期；
- 后台任务完成或失败；
- 继续执行需要关键决定；
- 已授权规则要求通知；
- 新信息显著改变当前计划；
- 用户主动配置了提醒。

普通低价值信息应留在 Activity Center，不主动抢占注意力。

## 8. 多分身模型

### 8.1 先验证上下文边界，再增加角色表达

首版不急于展示多个头像、声音或人格。它先提供两个受治理的 Context：

- **Work Context**：默认关联工作 Workspace、项目资料、工作记忆和工作能力策略。
- **Private Context**：默认关联个人资料、私人记忆和更严格的敏感数据策略。

Context 首先解决“当前任务可以使用哪些数据、能力和记忆”的问题，不创造新的 Enacta 身份，也不自动授予权限。早期界面应突出当前 Context、数据范围和授权状态，而不是突出角色装扮。

只有在以下证据成立后，才逐步增加语气、目标、主动策略和自定义 Persona：

- Work 与 Private 的敏感信息隔离可靠；
- 用户能理解切换 Context 不会扩大权限；
- 跨 Context 的最小必要共享可解释、可撤销；
- 角色差异确实减少沟通成本，而不只是带来新奇体验。

### 8.2 默认分身

成熟阶段的第一批分身建议包括：

**工作分身**

- 关注项目、交付、时间、风险和协作；
- 默认使用工作 Workspace、工作记忆和工作连接器；
- 表达简洁、明确、结果导向；
- 对外发送、部署和费用行为严格审批。

**生活分身**

- 关注个人计划、家庭、学习、健康和生活安排；
- 默认使用生活数据和个人偏好；
- 语气可以更温和，但不能伪装为具有人类情感；
- 对健康、财务等高敏感信息采用更严格的存储和访问策略。

**自定义分身**

用户可以创建“写作”“研究”“创业”“学习”等角色，并配置目标、语气、能力、记忆范围和主动程度。

### 8.3 Persona Profile

每个 Persona 至少具有：

```text
id
name
role description
communication style
goals and non-goals
default memory scopes
allowed capability profile
permission defaults
preferred views and artifacts
proactive behavior policy
created and modified provenance
```

### 8.4 分身切换

Persona 可以由用户显式切换，也可以由 Enacta 根据场景建议切换。

Enacta 可以说：

> 这个话题涉及个人旅行和工作报销。是否切换到生活分身处理行程，再让工作分身只读取经过你确认的报销信息？

涉及敏感范围变化时，不允许静默切换。

### 8.5 统一记忆不等于无限共享

所有 Persona 使用同一个受治理记忆基础，但每次检索必须同时满足：

- 当前 Persona 可访问该 Scope；
- 当前任务确实相关；
- 敏感级别允许使用；
- 权限未过期或撤销；
- 记忆没有被更正、否定、删除或标记过期。

生活中的敏感关系、健康和财务信息默认不能出现在工作分身中。工作分身可以知道“用户周五不可安排会议”，但不一定需要知道具体医疗原因。

### 8.6 分身不能扩大权限

切换 Persona 不会自动：

- 获得新的文件访问范围；
- 继承其他 Persona 的临时授权；
- 获得新的 Connector 写入权限；
- 绕过审批策略；
- 修改全局事实而不保留来源和冲突记录。

## 9. 统一记忆系统

### 9.1 记忆的产品目的

记忆不是为了保存所有对话，而是为了降低未来协作成本并提高结果质量。

值得长期记忆的信息通常包括：

- 用户明确要求记住的事实；
- 稳定偏好和工作方式；
- 反复使用并经过确认的背景；
- 长期项目及其关键决定；
- 重要人物和关系；
- 失败教训和用户纠正；
- 可复用的流程与验收标准。

不应默认进入长期记忆的内容包括：

- 一次性寒暄；
- 未经确认的模型推断；
- 临时尝试和草稿；
- 原始 hidden reasoning；
- Credential、Secret 和认证信息；
- 无界文件正文或录音；
- 与未来协作无关的低价值细节。

### 9.2 记忆类型

| 类型 | 示例 | 默认范围 |
| --- | --- | --- |
| 全局身份记忆 | 姓名、语言、稳定沟通偏好 | 全局，受敏感度限制 |
| 领域记忆 | 工作项目、生活计划、学习目标 | Work、Life 或自定义领域 |
| Persona 工作记忆 | 当前分身正在处理的短期上下文 | 当前 Persona 与任务 |
| 情景记忆 | 一次会议、讨论或决策经过 | 按来源和项目范围 |
| 语义记忆 | 已确认事实、概念和关系 | 按事实 Scope |
| 偏好记忆 | 汇报格式、表达风格、工具偏好 | 全局或 Persona |
| 项目记忆 | 目标、人员、约束、决定和状态 | 项目 Scope |
| 程序记忆 | 经过验证的操作流程和模板 | 能力与权限 Scope |

### 9.3 每条长期记忆的最小属性

```text
memory id
content or structured value
type
scope
source and provenance
confidence
importance
sensitivity
created / confirmed / last-used time
correction and contradiction state
retention and expiry policy
status
```

重要记忆不能只依赖不可解释的向量相似度或模型直觉。

### 9.4 首版记忆契约

首版不要求用户理解完整的权重、衰减和压缩模型，只需要让六件事始终清楚：

1. Enacta 记住了什么；
2. 信息来自哪里；
3. 为什么在当前任务中使用；
4. 如何纠正；
5. 如何要求暂时不使用；
6. 如何永久删除。

首版优先采用显式记忆候选和周期性记忆摘要。例如每周集中展示“Enacta 本周学到了什么”，让用户批量接受、修改、调整 Scope 或删除，避免每轮对话都弹出确认。

自动召回排序可以在首版内部保持保守，但自动衰减、跨记录压缩和复杂强化必须等到真实纠正与召回数据产生后再逐步启用。成熟记忆模型仍是长期方向，首版简化的是交互和自动化程度，而不是数据来源、敏感度和用户控制边界。

### 9.5 记忆候选与确认

对话中出现的信息先成为记忆候选。Enacta 根据重要性和风险决定处理方式：

- 低风险偏好：可以轻量提示后写入；
- 项目事实：记录来源和置信度；
- 重要决定：要求用户确认；
- 高敏感信息：默认不写入长期记忆，除非用户明确选择；
- 模型推断：必须标记为推断，不能冒充用户事实。

示例：

> 我将记住：正式汇报先给结论，再给依据。范围：工作分身。你可以随时修改或忘记。

### 9.6 记忆召回权重

记忆召回应使用可解释的产品策略：

```text
召回价值 ≈
任务相关性
× Scope 可访问性
× 重要性
× 可信度
× 新鲜度
× 使用强化
− 敏感度惩罚
− 过期、冲突和否定惩罚
```

实际实现可以采用不同算法，但必须能够向用户解释“为什么想起这件事”。

### 9.7 记忆控制中心

用户需要一个明确入口查看 Enacta 记得什么：

- 按全局、领域、项目和 Persona 浏览；
- 查看来源和最近使用时间；
- 查看为什么被召回；
- 修改错误信息；
- 确认或取消推断；
- 固定重要记忆；
- 调整 Scope 和敏感级别；
- 要求暂时不使用；
- 遗忘、删除或导出；
- 查看自动压缩和到期策略。

### 9.8 遗忘不是一个动作

V2 区分六种不同的记忆变化：

1. **上下文排除**：本次任务不使用，但记忆仍然存在。
2. **降低召回权重**：未来只有在高度相关时才使用。
3. **衰减**：随着时间和低使用频率逐步降低优先级。
4. **压缩**：把多段低价值情景记录整合为更短摘要，同时保留来源边界。
5. **到期或归档**：根据用户设置停止主动召回，但可恢复或查询。
6. **永久删除**：移除对应记忆及允许移除的派生索引。

模型不能因为判断“似乎不重要”就自行永久删除持久数据。永久删除需要用户操作或用户明确配置的保留策略。

### 9.9 更正优先于重复

当用户更正记忆时：

- 新事实获得明确的 correction provenance；
- 旧事实被标记为 superseded 或 disputed；
- 后续召回优先使用已确认的新事实；
- 不通过简单新增一条矛盾记录来逃避冲突处理；
- 必要时提示受旧事实影响的未完成任务。

## 10. 从意图到成果的工作循环

Enacta 使用统一的 Outcome Loop 推进工作：

```text
捕获 Capture
→ 理解 Understand
→ 澄清 Clarify
→ 申请能力与权限 Authorize
→ 规划 Plan
→ 执行 Execute
→ 呈现 Present
→ 审核 Review
→ 提交 Commit
→ 学习 Learn
→ 继续或恢复 Resume
```

### 10.1 Outcome 完成契约

每个有实际交付责任的 Outcome 都应逐步形成一份完成契约：

| 字段 | 说明 |
| --- | --- |
| 目标成果 | 最终需要形成什么 Artifact、决定或外部结果 |
| 验收条件 | 用户用什么标准判断结果可以接受 |
| 数据与能力 Scope | 可以读取、调用和修改的明确边界 |
| 时间与成本约束 | 截止时间、预算和运行限制 |
| 等待用户事项 | 尚未确认的决定、授权或必要信息 |
| 完成证据 | 文件、预览、校验、来源、运行结果或用户确认 |
| 结果状态 | `complete`、`partial`、`failed`、`cancelled` 或 `needs_review` |

Enacta 不能因为生成了一段回答、创建了一份计划或写出了文件就自动宣称完成。只有验收条件成立且不存在必要的未决用户决定时，Outcome 才能进入 `complete`。无法确认质量、外部效果不确定或证据不足时进入 `needs_review`；完成部分交付但未满足全部条件时进入 `partial`。

简单任务可以使用轻量契约，复杂或高风险任务需要用户明确确认。契约的目的不是增加表单，而是让用户和 Enacta 对“做完了”拥有同一个定义。

### 10.2 捕获

输入可以来自文字、按键语音、文件、画布、外部数据或已授权事件。原始输入保留必要来源，但不会全部自动变为长期记忆。

### 10.3 理解与澄清

Enacta 识别目标、限制、期望成果、截止时间、参与者和风险。信息不足时，应优先询问会改变结果的重要问题，避免把沟通变成冗长问卷。

### 10.4 申请能力与权限

Enacta 解释为什么需要某项能力、将访问哪些数据、会产生什么影响、授权持续多久以及能否撤销。

### 10.5 规划与执行

简单任务可以直接执行；复杂任务形成可见计划、后台 Job 或 Workflow。计划不是形式要求，而是帮助用户理解目标、依赖、风险和当前状态。

### 10.6 呈现与审核

Enacta 根据数据和任务选择最合适的 View。用户可以在对话、编辑器或生成视图中检查结果，并通过自然语言或直接编辑修正。

### 10.7 提交

只有经过既定权限、校验和事务边界的结果才进入正式 Artifact、外部系统或已完成 Outcome。

### 10.8 学习

完成后，Enacta 可以提出记忆候选：哪些偏好、决定、流程和错误值得保留。用户可以接受、修改或拒绝。

## 11. 视图和编辑器编排

### 11.1 视图选择原则

Enacta 根据以下条件选择呈现方式：

- 用户需要回答、浏览、编辑还是共同构思；
- 数据是否具有稳定 Schema；
- 是否存在注册编辑器；
- 结果是临时分析还是长期 Artifact；
- 是否需要事务、验证和原生 Undo/Redo；
- 是否需要导出、分享或继续维护；
- 生成视图是否能够满足安全和可访问性要求。

### 11.2 对话内组件

适合：

- 简单问题和结论；
- 少量选项；
- 权限请求；
- 任务状态；
- 小型表格和指标；
- 记忆候选和纠正。

### 11.3 Markdown

适合：

- 研究、说明、会议纪要和长文本；
- 可版本管理的结构化文字；
- 用户需要逐段修改的成果；
- 长期保存和跨工具迁移。

### 11.4 IdeaSketch

适合：

- 用户难以完全用语言表达的想法；
- 结构、关系、流程和空间布局；
- 人与 Enacta 共同形成理解；
- 演示、图示和视觉草图。

IdeaSketch 不只是展示工具，也是共同思考的白板。

### 11.5 领域编辑器

任务、表格、Workflow、应用或未来业务数据应优先使用稳定注册编辑器，以获得 Schema、验证、事务、Undo/Redo 和长期维护能力。

### 11.6 生成 Web View

当不存在合适编辑器，或用户需要一次性分析、仪表板、交互原型和特殊可视化时，Enacta 可以生成受隔离的 Web View。

每个生成视图必须说明：

- 数据来源；
- 是否为临时视图；
- 关闭后是否保留；
- 修改的是视图参数还是底层数据；
- 是否包含推断；
- 能否导出为 HTML 或正式 Artifact；
- 使用了哪些权限；
- 是否可以安全重新生成。

生成 Web View 默认运行在无权限沙箱中，不能因为呈现需要而获得文件、网络、Secret、进程或编辑器写入权限。

### 11.7 从临时视图沉淀为稳定能力

某类生成视图如果高频出现、需要长期维护或包含重要业务规则，应演进为：

- 可复用模板；
- 注册编辑器；
- Workflow；
- Plugin；
- 正式应用。

## 12. Workspace 的新角色

Workspace 在 V2 中仍然重要，但从默认主界面变为一个随时可进入的工作空间。

用户可以：

- 从 Agent Home 点击进入 Workspace；
- 从某个 Outcome 打开关联文件；
- 查看 Enacta 使用了哪些资料；
- 直接编辑、移动、版本管理和导出真实文件；
- 审查 Agent 生成的 Artifact；
- 在不使用 Agent 时继续使用编辑器。

Workspace 保留 V1 的核心原则：

- 真实文件是用户 Artifact 的事实来源；
- 双模式、单内核；
- 延迟元数据；
- 注册表驱动编辑器；
- 本地优先和安全写入；
- 外部变化不能被静默覆盖；
- 编辑器原生事务与 Undo/Redo。

## 13. 权限、审批与人类权威

### 13.1 权限请求应说明工作目的

不使用抽象系统提示：

> Enacta 请求文件夹权限。

应说明：

> 为生成本周项目汇报，我需要读取 `Project A/reports` 中过去七天修改的 Markdown 文件。仅本次任务使用，不会读取其他目录，也不会修改文件。

用户可以选择：

- 允许本次；
- 在该项目和目的内持续允许；
- 查看或缩小数据范围；
- 拒绝并改用用户提供的内容。

### 13.2 Grant 必须有边界

每项授权至少包含：

- 目的；
- Capability；
- 数据或资源 Scope；
- Persona；
- 有效时间；
- 风险等级；
- 是否可复用；
- 撤销方式；
- 审计记录。

### 13.3 权限需要通过成果逐步获得

Enacta 不在首次启动时索取广泛权限，而是随着用户看到真实价值逐步建立授权关系：

| 授权阶段 | 默认范围 | 适用场景 |
| --- | --- | --- |
| P0 用户提供 | 只使用本轮文字、语音转写或拖入内容 | 首次尝试和敏感任务 |
| P1 单次任务 | 一个文件、一个目录或一个 Connector 查询，仅本次有效 | 首个 Outcome |
| P2 项目目的 | 在一个项目和明确目的内重复使用，可随时撤销 | 已重复成功的工作流 |
| P3 规则内委托 | 带时间、预算、频率和 Human Gate 的持续授权 | 后台 Job 和周期任务 |

从 P0 到 P3 不是自动升级。每次扩大权限都应说明过去哪些成果证明了价值、新范围能减少什么摩擦，以及增加了什么风险。用户拒绝扩大权限时，Enacta 继续在原范围内工作或明确说明限制。

每次产生文件修改、外部效果、重要决定或长期记忆候选后，Enacta 提供一份紧凑的行动回执：

- 本次目的；
- 使用的数据与来源；
- 调用的 Capability；
- 执行和修改的内容；
- 支持结果的证据与推断；
- 是否可以撤销、恢复或重新生成；
- 建议保留的记忆候选；
- 尚未完成或需要审核的事项。

行动回执不是冗长日志，而是用户判断“这件事是否真的完成、是否值得继续信任”的最小证据。

### 13.4 渐进自治

Enacta 的自治等级建议为：

| 等级 | 行为 |
| --- | --- |
| L0 回答 | 仅提供信息，不执行变化 |
| L1 准备 | 生成草案、计划或预览，等待用户决定 |
| L2 确认后执行 | 每次重要行为获得确认后执行 |
| L3 规则内执行 | 在明确 Scope、预算和时间内自动执行，异常时停止 |
| L4 委托工作 | 执行持久化 Workflow 或专业 Agent 协作，保留人工门和审计 |

V2 不定义无边界 L5 自治。

### 13.5 用户可以随时接管

用户始终可以：

- 暂停或取消；
- 修改计划；
- 撤销授权；
- 直接编辑 Artifact；
- 拒绝记忆候选；
- 要求解释来源；
- 重试、恢复或终止后台工作。

## 14. 声音与环境式存在

### 14.1 声音入口

声音是降低表达成本的重要入口，但初期采用主动触发：

- 按住说话；
- 全局快捷键；
- 明确开始和结束录音；
- 可见录音状态；
- 用户选择是否保存原始音频。

持续监听默认关闭，并且不能作为 V2 初期依赖。

### 14.2 声音处理层次

```text
原始音频
→ 带时间信息的转写
→ 语义整理
→ 决定、任务、事实和记忆候选
→ 用户确认
→ 执行或长期保存
```

### 14.3 桌面 Pet 与环境式存在

桌面 Pet 是远期表达“Enacta 持续存在”的可选形态，不是核心价值。

它必须：

- 默认不持续打扰；
- 可完全关闭；
- 不使用动画制造虚假忙碌；
- 只在需要决定、任务完成、错误或用户配置提醒时出现；
- 不默认监听麦克风或观察屏幕；
- 不通过过度拟人化制造情感依赖。

真正让 Enacta 像同事的不是形象，而是理解、信任和完成工作。

## 15. 核心产品能力

### 15.1 Agent Home 与持续任务

- 统一文字和语音入口；
- “今天、等待我、正在推进、最近成果”四个稳定区域；
- 当前 Context、成熟阶段的 Persona 与数据范围；
- Outcomes、后台 Jobs、行动回执和等待事项；
- 对话、Activity、权限和成果；
- 跨重启恢复和继续。

### 15.2 记忆管理

- 首版的记忆候选、来源、为什么使用、纠正、暂不使用和删除；
- 周期性记忆摘要和批量审查；
- 来源、Scope、可信度和重要性；
- 成熟阶段的固定、重设范围、衰减和压缩；
- 为什么召回；
- 导出和隐私控制。

### 15.3 Persona 管理

- 首版 Work 与 Private Context；
- Context 的数据、能力、记忆和权限申请边界；
- Work、Life 和自定义角色；
- 角色目标、语气和输出偏好；
- Capability 与 Permission Profile；
- 记忆 Lens 和数据范围；
- 明确切换与建议切换。

### 15.4 Outcome 管理

- 目标、期望 Artifact、验收标准、Scope、期限和成本约束；
- 计划、依赖、状态和风险；
- Artifacts、证据和来源；
- 等待用户的决定和审批；
- `complete`、`partial`、`failed`、`cancelled`、`needs_review` 和恢复；
- 证明结果和权限使用情况的行动回执。

### 15.5 编辑器与 View Router

- 选择对话组件、Markdown、IdeaSketch、领域编辑器或 Web View；
- 解释为什么选择该形式；
- 维持临时 View 与正式 Artifact 的区别；
- 通过注册表扩展新能力。

### 15.6 Workspace 与真实文件

- 按需打开 Workspace；
- 安全读取、搜索、Diff、修改、移动和 Trash；
- 真实文件、原子保存、Recovery 和外部冲突保护；
- 用户可以脱离 Agent 继续工作。

### 15.7 后台 Job 与 Workflow

- 持久化状态；
- 截止时间、预算、重试和取消；
- Checkpoint 与恢复；
- Human Gate；
- 周期性和事件触发工作；
- 可见成本和失败原因。

### 15.8 专业 Agent 和 Plugins

- 研究、编码、设计或业务专业 Agent；
- 受限上下文和 Capability Grant；
- 返回可审查 Artifact 或 ChangeSet；
- 不直接成为 Enacta 数据、权限和生命周期权威。

## 16. 代表性使用场景

这些场景不是并列功能清单，而是形成“第一次价值—重复留存—高频入口”的用户成长路径。

### 16.1 首发获客闭环：模糊汇报想法到 HTML 成果

用户对工作分身说：

> 我要做一个季度汇报，脑中有大概结构，但说不清楚。

Enacta：

1. 询问受众、目标和交付时间。
2. 判断纯文字不足以形成共同理解。
3. 建议打开 IdeaSketch：“我们先一起画结构。”
4. 用户在画布中绘制“现状—问题—原因—方案—结果”。
5. Enacta 在授权范围内读取当前画布结构，并复述理解。
6. 用户纠正其中一处关系。
7. Enacta 读取经过授权的数据并生成 HTML 汇报。
8. 使用受隔离 Web View 展示预览，标明数据来源和推断。
9. 用户审核后导出真实 HTML Artifact。
10. Enacta 提出记忆候选：“正式汇报先结论、再依据，并优先使用深色简洁风格。”

有效结果不是一段建议，而是一份经过共同澄清、可继续维护的汇报。

### 16.2 高频入口：语音到项目行动

用户通过快捷键说：

> 下个月发布新产品，需要市场调研、落地页、发布内容和每周检查。

Enacta 保存经用户允许的转写，识别目标、时间和交付物，创建 Outcome 与任务计划，询问关键假设，生成说明文档，并持续跟踪等待事项。

### 16.3 留存闭环：Workspace 到周报

用户授权 Enacta 读取项目目录过去七天的变更。Enacta 汇总真实文件、任务和运行记录，区分已完成、风险和下一步，在发送前请求确认，并将用户修正沉淀为周报偏好。

### 16.4 生活与工作分身协作

生活分身知道用户周五下午有私人安排。工作分身在排会议时只获得“该时间不可用”的全局可用性事实，不读取私人事件内容。

如果用户需要报销旅行费用，生活分身先整理行程和票据，用户确认后，仅将必要的日期、金额和凭证 Artifact 授权给工作分身。

### 16.5 记忆纠正与遗忘

Enacta 根据旧记录认为某客户偏好 PDF。用户说：“他们现在只要在线链接。”

Enacta：

- 将旧偏好标记为已被替代；
- 记录新偏好的来源和确认时间；
- 检查是否有未完成任务仍准备输出 PDF；
- 询问是否需要批量调整；
- 后续不再召回旧偏好作为当前事实。

### 16.6 周期性行业简报

用户明确授权工作分身每周读取指定来源、生成简报，并在发布前等待确认。Job 在应用重启后恢复，超过预算、来源失败或出现高敏感信息时暂停，而不是静默跳过。

## 17. 产品信息架构

### 17.1 顶层结构

V2 顶层以四个稳定工作区域构成 Agent Home，其余能力通过明确入口进入：

```text
Enacta Agent Home
├── Today
├── Waiting for Me
├── In Progress
├── Recent Outcomes
├── Conversation and Voice
└── Open
    ├── Workspace and Artifacts
    ├── Memory
    ├── Contexts and Personas
    ├── Activity and Jobs
    └── Settings
```

稳定区域回答“现在有什么值得关注”；入口回答“我需要深入查看什么”。动态生成的组件和 View 只能出现在具体任务或成果内部，不能让用户每次打开产品都重新学习导航。

### 17.2 主要工作布局

默认状态以 Agent 为主体：

```text
┌─────────────────────────────────────────────────────────────┐
│ Enacta · Work Context · Current scope · Global controls    │
├─────────────────────────────────────────────────────────────┤
│ Today · Waiting for Me · In Progress · Recent Outcomes     │
│                                                             │
│ Conversation, activity, cards and generated views          │
│                                                             │
│ Text / Push-to-talk composer                                │
└─────────────────────────────────────────────────────────────┘
```

需要共同编辑时，View 在 Agent 旁边或主区域打开，而不是让对话上下文消失：

```text
┌──────────────────────────┬──────────────────────────────────┐
│ Enacta conversation      │ Markdown / IdeaSketch / Web View │
│ Plan and activity        │                                  │
│ Questions and decisions  │ Human and Agent shared surface   │
└──────────────────────────┴──────────────────────────────────┘
```

Workspace 通过明确入口进入，可以替换或展开为文件管理模式，但 Agent 的任务上下文仍可恢复。

## 18. 架构与数据边界

V2 产品形态建立在 RFC 003 的 Enacta Agent Kernel 之上。

### 18.1 Kernel 权威

Kernel 负责：

- Thread、Turn、Item、Job、Workflow 和子 Agent 生命周期；
- 有序事件、持久化和恢复；
- Tool 注册、Schema、策略、审批和结果归一化；
- 取消、截止时间、预算、重试和幂等；
- Plugin、Provider 和专业 Agent 边界；
- 记忆与活动的脱敏持久化策略；
- 编辑器和 Workspace 能力路由。

### 18.2 V2 新增的产品服务概念

V2 后续架构需要进一步定义：

- Persona Registry；
- Memory Service 与 Memory Policy；
- Outcome Store；
- Context and Memory Retrieval；
- View Router；
- Permission Grant Manager；
- Notification and Interruption Policy；
- User-facing Memory Control Center。

本说明书只定义产品契约，不指定最终存储引擎或实现技术。

### 18.3 编辑器权威不变

Agent 对活动编辑器的修改继续遵守：

- 当前文档绑定；
- revision、digest 和 fingerprint 检查；
- 只读和外部变化保护；
- 编辑器原生事务；
- 原生 Undo/Redo；
- 正常保存和 Recovery 生命周期。

Persona、Memory 或生成 View 都不能绕过这些边界。

## 20. 用户期望权重模型

V2 不按技术炫酷程度排序，而按用户是否愿意把真实任务交给 Enacta 排序。

### 20.1 评分维度

| 维度 | 权重 | 核心问题 |
| --- | ---: | --- |
| Outcome 完成与质量 | 30% | 是否真正把事情推进到可接受结果？ |
| 信任、控制、隐私和可恢复性 | 25% | 用户是否敢把真实数据和行为交给它？ |
| 高频使用与摩擦降低 | 15% | 是否减少日常表达、查找和操作成本？ |
| 记忆复利与个性化 | 15% | 是否越用越懂用户并减少重复沟通？ |
| 能力复用与扩展性 | 10% | 是否能支持更多场景而不破坏内核？ |
| 愉悦感、陪伴感和新奇体验 | 5% | 是否提升情感体验但不替代核心价值？ |

每项能力按 1–5 分评估，计算 0–100 的加权用户期望分。技术依赖和安全门可以调整阶段，但不能掩盖用户价值排序。

后台和周期性 Job 的原始用户价值较高，但由于副作用、恢复和信任依赖，被明确推迟到 Phase 4。

### 20.3 排序规则

1. 高分能力原则上优先。
2. 信任和数据安全是硬门，不因业务分数高而跳过。
3. 能复用已交付能力的闭环优先于全新基础设施。
4. 每个阶段必须先验证用户结果，再扩大自治。
5. 真实使用证据可以重新排序后续能力。
6. 新奇体验不能以牺牲稳定性、可解释性和可恢复性为代价。

## 21. 分阶段产品路线

路线按能力成熟和用户证据推进，不等同于固定发布日期。

### Phase 1：一个可信的完整成果闭环

**目标：** 新用户能够在有限授权内把一个模糊想法交给 Enacta，并获得一份可审核、可修改、可保存为真实文件的成果。

**主导用户期望权重：** Outcome 完成与质量 30%，信任、控制、隐私和可恢复性 25%，高频使用与摩擦降低 15%。

**前置条件：** V1 的 Workspace、真实文件、编辑器内核与基础 Agent 能力保持可用；RFC 003 的 Kernel、权限和持久化边界进入后续实施设计。

能力：

- 具有“今天、等待我、正在推进、最近成果”四个稳定区域的 Agent Home；
- 文字优先的沟通入口；
- 首次十分钟体验；
- 模糊想法 → IdeaSketch → HTML 或文档的完整首发闭环；
- Outcome 完成契约、等待事项和 Activity；
- P0/P1 窄范围授权和目的明确的权限请求；
- 行动回执；
- 取消、失败、恢复和用户接管；
- Workspace 入口和真实文件关联；
- 现有 Markdown、IdeaSketch 的按需调用；
- 受隔离的有限 HTML View 和真实 Artifact 导出；
- 基础记忆候选、来源查看、为什么使用、纠正、暂不使用和删除；
- Work/Private Context 与数据范围展示，但暂不追求人格化多分身。

进入下一阶段的证据门：

- 用户能理解 Agent Home，而不是把它当成空白聊天框；
- 新用户能在十分钟内看到可判断的成果、明确下一步或真实阻塞；
- 首发场景形成满足完成契约、可追溯到真实文件的 Outcome；
- 大部分试用用户能够审核、修改或接受首个 Artifact；
- 权限请求能被正确理解和接受或缩小；
- 用户能从行动回执理解 Enacta 使用了什么、改变了什么以及能否撤销；
- 失败和取消不会造成重复副作用；
- 基础记忆没有严重错误或隐私泄露；
- 用户愿意把第二个真实任务继续交给 Enacta。

### Phase 2：重复使用与三个有效任务闭环

**目标：** 证明首发成果不是一次性演示，并通过 Workspace 和语音让 Enacta 进入重复工作。

**主导用户期望权重：** Outcome 完成与质量 30%，高频使用与摩擦降低 15%，记忆复利与个性化 15%。

**前置条件：** Phase 1 的首个完整 Outcome、行动回执、权限、取消恢复、基础记忆控制和按需编辑器达到证据门要求。

能力：

- 首发 IdeaSketch 闭环的质量、速度和重复执行优化；
- Workspace 到周报、汇报和下一步行动的留存闭环；
- 按键语音到项目计划、决定和任务的高频闭环；
- P2 项目目的授权；
- 周期性记忆摘要与批量纠正；
- 记忆来源、召回理由和用户纠正；
- Artifact 导出、继续编辑和结果验收；
- 结果质量、耗时、成本和修改幅度统计。

进入下一阶段的证据门：

- 首发闭环被同一用户再次使用，而不是只在引导中完成一次；
- Workspace 和语音闭环都有真实用户重复使用；
- 大部分成果被接受、继续编辑或实际交付；
- 用户愿意从 P1 单次授权主动扩大到有边界的 P2 项目授权；
- 用户修改幅度和澄清轮数随着使用下降；
- 语音录制、转写和保存边界被用户理解；
- 生成 View 没有取代正式 Artifact 或产生安全混淆。

### Phase 3：记忆复利与多分身

**目标：** 让 Enacta 越用越懂用户，同时保持工作、生活和敏感信息边界。

**主导用户期望权重：** 信任、控制、隐私和可恢复性 25%，记忆复利与个性化 15%，高频使用与摩擦降低 15%。

**前置条件：** Phase 2 已产生足够的真实记忆候选、纠正、召回和敏感场景证据，可以验证排序与隔离策略，而不是只依赖模型假设。

能力：

- 完整记忆类型、Scope 和生命周期；
- 重要性、可信度、新鲜度和重复强化；
- 衰减、压缩、到期、归档和删除；
- 为什么召回；
- Work、Life 和自定义 Persona；
- 从已验证的 Work/Private Context 演进为更丰富的角色表达；
- Persona 切换和建议切换；
- 跨 Persona 的最小必要信息共享；
- 记忆导出和隐私审查。

进入下一阶段的证据门：

- 用户明显减少重复背景说明；
- 重要记忆正确率和纠正率达到产品要求；
- 不出现敏感 Life 信息意外进入 Work 场景；
- 用户理解 Persona 是同一个 Enacta 的不同角色；
- Persona 切换不会扩大权限；
- 自动衰减和压缩可解释、可恢复或符合明确策略。

### Phase 4：主动协作与后台工作

**目标：** Enacta 在明确规则内持续推进工作，而不是只在用户发消息后行动。

**主导用户期望权重：** Outcome 完成与质量 30%，信任、控制、隐私和可恢复性 25%，高频使用与摩擦降低 15%。

**前置条件：** Phase 3 的记忆准确性、Persona 隔离、权限不扩张和用户控制均达到证据门要求；Kernel 的持久化 Job、幂等、预算和恢复机制可供实施。

能力：

- 持久化 Job 和 Workflow；
- 周期性简报和检查；
- Trigger；
- Checkpoint、恢复、预算和幂等；
- Human Gate；
- 有限主动提醒；
- 多步骤任务与单一受控专业能力委派，不包含通用多 Agent 编排；
- Job Center 与打扰策略。

进入下一阶段的证据门：

- 后台任务不会重复副作用；
- 用户能理解并控制主动行为；
- 通知拒绝、关闭和撤销率处于可接受范围；
- 失败、恢复和成本可解释；
- 自动执行仍遵守 Scope、预算和权限。

### Phase 5：环境式同事与能力生态

**目标：** 在核心信任和任务价值已经成立后，扩展产品形态和长尾能力。

**主导用户期望权重：** 能力复用与扩展性 10%，愉悦感、陪伴感和新奇体验 5%；任何扩展仍受前四类共计 85% 的核心期望约束。

**前置条件：** 前四阶段已证明稳定留存、可信 Outcome、受治理记忆和可控后台工作；插件供应链、生成 UI 和环境式入口分别完成安全与可访问性设计。

候选能力：

- 可选桌面 Pet；
- 环境式状态和跨窗口入口；
- 更丰富的生成 Web UI；
- 稳定 View 模板和生成系统；
- Plugin SDK 与签名插件；
- 更多领域编辑器；
- 多 Agent 编排和 Specialist 生态；
- 可移植 Persona 与 Memory Policy。

进入生态扩张的证据门：

- 核心 Outcome 留存已经稳定；
- 用户不会把 Enacta 仅理解为聊天工具；
- 插件隔离、签名、撤销和兼容性经过验证；
- 生成 UI 可访问、可解释并有稳定回退；
- 桌面存在感不会显著增加打扰和关闭率。

## 22. 成功指标

### 22.1 北极星指标

> **每周由 Enacta 推进并被用户接受的真实 Outcomes 数量。**

### 22.2 激活与首个价值指标

- 从首次打开到开始第一个真实任务的比例；
- 从首次表达 Intent 到出现可判断中间成果的时间；
- 在十分钟内看到成果、明确下一步或真实阻塞的比例；
- 首个 Artifact 被接受、修改后接受或保存为真实文件的比例；
- 首次用户是否理解四个 Agent Home 区域；
- 首次用户是否能说明 Enacta 使用了哪些数据和权限；
- 完成首个 Outcome 后七天内提交第二个真实任务的比例。

### 22.3 Outcome 指标

- 从首次表达 Intent 到第一个有效 Artifact 的时间；
- 任务真正完成而非仅创建计划的比例；
- Agent 成果被接受、编辑、拒绝和实际交付的比例；
- 用户需要重新解释背景的次数；
- 用户对成果的修改幅度；
- 同类任务重复执行时的沟通轮数下降。

### 22.4 信任指标

- 权限允许、缩小、拒绝和撤销比例；
- 用户是否理解权限目的和数据范围；
- 重复副作用、错误写入和恢复失败率；
- 取消和暂停成功率；
- 用户查看来源和审计信息的行为；
- 用户能否理解行动回执中的目的、数据、修改、证据和撤销方式；
- 用户从 P0/P1 主动扩大到 P2/P3 授权的比例及其后续撤销率；
- 高风险操作是否正确经过审批。

### 22.5 记忆指标

- 记忆候选接受、修改和拒绝比例；
- 记忆被召回后的正确、有用和不相关比例；
- 用户主动固定、调整 Scope、遗忘和删除的数量；
- 陈旧或矛盾记忆被正确处理的比例；
- Persona 间敏感信息错误披露率；
- 记忆是否实际减少重复沟通。

### 22.6 留存指标

- 用户是否持续把新的真实任务交给 Enacta；
- 同一 Outcome 跨多天继续推进的次数；
- 被持续维护的 Artifacts 和 Workflows 数量；
- 从一次成功操作沉淀为模板、记忆或自动化的比例；
- 用户在 Agent Home、Workspace 和编辑器之间完成的闭环数量。

### 22.7 不作为核心成功指标

- 对话次数；
- 生成字数；
- 在线时长；
- Persona 数量；
- 生成 View 数量；
- 桌面 Pet 点击次数；
- 未被采用的计划和任务数量。

## 23. 信任、安全与隐私

### 23.1 数据最小化

- 只获取完成当前目的所需的数据；
- 不因为“未来可能有用”默认保存所有内容；
- 对敏感数据使用更短上下文和更严格记忆策略；
- Credential、Secret 和隐藏 reasoning 不进入记忆、对话或诊断。

### 23.2 来源与推断分离

Enacta 必须区分：

- 用户明确陈述；
- 文件或外部系统事实；
- Agent 推断；
- 未确认假设；
- 已被更正或否定的信息。

### 23.3 本地优先

记忆、Thread、权限和 Activity 默认存储在用户设备上的应用数据目录。需要远程模型、同步或连接器时，产品说明发送的数据、目的和处理方。

### 23.4 可导出与可删除

用户可以导出自己的记忆、设置、Threads、Outcomes 和可导出的 Artifacts，并可以删除不再需要的应用数据。删除边界和无法控制的外部副本必须如实说明。

### 23.5 跨 Context 与 Persona 隔离

统一记忆底座必须执行 Scope 和敏感度过滤。任何跨 Context 或 Persona 共享都保留目的、来源和授权证据。

## 24. 产品风险与缓解措施

| 风险 | 缓解措施 |
| --- | --- |
| 产品变成另一个聊天客户端 | 以 Outcome、等待事项、成果和后台状态构成 Agent Home，不以空白聊天为中心。 |
| “AI 同事”承诺过宽 | Phase 1 只证明一个完整首发闭环，并让用户通过连续成果逐步形成同事认知。 |
| 基础设施完整但用户感受不到价值 | Phase 1 同时交付首个真实 Artifact，不把完整成果推迟到后续阶段。 |
| 首次配置和授权过重 | 采用十分钟体验、P0/P1 窄授权、Context 默认值和渐进权限扩展。 |
| Agent 错误宣称任务完成 | 使用 Outcome 完成契约、验收条件、完成证据和 `partial`、`needs_review` 等诚实状态。 |
| 记忆错误破坏信任 | 记忆候选、来源、可信度、纠正、Scope、为什么召回和用户控制。 |
| 生活隐私泄露到工作 | Domain Scope、敏感度、Persona Lens、最小必要共享和显式授权。 |
| 多分身成为头像和 Prompt 噱头 | 分身必须真正改变目标、能力策略、默认权限申请范围和记忆视角，同时保持同一 Enacta 身份；切换本身不得扩大已有授权。 |
| 自动遗忘删除重要信息 | 区分排除、衰减、压缩、归档、到期和删除；永久删除由用户或明确策略控制。 |
| 动态 UI 造成不稳定 | 高频和长期数据优先稳定编辑器；生成 View 只用于长尾和临时场景。 |
| 主动行为令人厌烦 | 默认克制、集中 Activity、可配置通知、明确关闭入口和打扰指标。 |
| 桌面 Pet 变成噱头 | 推迟到核心价值验证后，可关闭，不默认监听或观察。 |
| 后台任务重复副作用 | Kernel 幂等、Checkpoint、Tool Outcome、预算、取消和 needs-review 状态。 |
| 用户不理解 Agent 使用了什么 | 显示当前 Context 或 Persona、Scope、来源、Capability、Activity、审批记录和行动回执。 |
| 本地优先限制模型能力 | 清楚区分本地数据控制与远程能力，采用最小发送和可替换 Provider。 |
| 功能路线被愿景绑死 | 使用用户期望评分和阶段证据门，允许基于真实数据重新排序。 |

## 25. 明确边界与非目标

Enacta V2 不以以下目标为当前承诺：

- 记住用户说过的一切；
- 模拟具有真实情感或主体性的数字生命；
- 替用户承担法律、财务、医疗或组织责任；
- 在用户不知情时持续监听、观察或记录；
- 首次启动就要求整个磁盘、全部历史或长期外部写入权限；
- 让 Persona 成为权限逃逸机制；
- 用生成 UI 替代所有稳定软件；
- 默认运行任意 Shell、脚本、网络和部署操作；
- 未经审核向外部发送消息、交易或生产变更；
- 用应用数据库替代用户真实文件；
- 展示或持久化 raw chain-of-thought；
- 在早期阶段建设开放插件市场；
- 一次性交付全部 V2 愿景。

## 26. 阶段决策机制

每个阶段进入实施前，需要单独完成：

1. 用户问题和目标人群确认；
2. 对应 PRD 或 RFC；
3. 数据、记忆、权限和失败边界；
4. 可观测的验收标准；
5. Superplan 计划评审；
6. 小范围真实用户验证；
7. 结果、信任和风险指标复盘；
8. 是否继续、调整、推迟或取消的决策。

优先级不是一次性结论。以下证据可以触发重新排序：

- 用户反复提出同一未满足需求；
- 某项能力显著提高 Outcome 完成率；
- 某项能力产生不可接受的隐私或信任问题；
- 新技术降低关键能力的实现和运行成本；
- 现有功能使用率低或无法形成留存；
- 新的依赖条件已经成熟。

## 27. 品牌表达

### 27.1 产品类别

推荐类别表达：

> **Personal AI Colleague**

中文：

> **个人 AI 同事**

在需要解释技术属性时可以补充：本地优先、Agent-first、以真实文件和受治理记忆为基础。

### 27.2 推荐口号

主口号：

> **Turn intent into outcomes.**

关系表达：

> **Think with me. Work with me. Grow with me.**

中文表达：

> **和你一起想，把事情做成。**

### 27.3 标准产品描述

短版：

> Enacta 是一个理解你、记得你，并把模糊意图推进为真实成果的个人 AI 同事。

长版：

> Enacta 是一个本地优先、持续存在的个人 AI 同事。用户通过文字或声音表达目标，Enacta 在明确权限内使用数据、记忆、工具和专业能力推进工作，并在需要共同思考、审核或交付时按需打开 Markdown、IdeaSketch、领域编辑器或受隔离 Web 视图。它支持工作、生活和自定义角色分身，共享一个可查看、可纠正、可遗忘的记忆基础，同时保留真实文件、编辑器事务和人类最终决定权。

## 28. 最终定义

Enacta V2 不是一个带有更多 AI 功能的 Workspace，也不是拥有多个头像的聊天软件。

> **Enacta 是一个持续理解用户、受治理地记住重要信息、根据场景采用不同角色，并把意图推进为真实成果的个人 AI 同事。**

它的核心承诺是：

> **用户负责表达愿望、提供判断并作出关键决定；Enacta 负责理解、记忆、组织、执行、呈现和持续推进。**

它的产品优先级始终服从三个词：

> **理解、信任、完成。**
